# VNami — Architecture

> Функціонал і рішення щодо продукту описано в [OVERVIEW.md](OVERVIEW.md), формат даних — у [SCHEMA.md](SCHEMA.md), MCP — у [MCP.md](MCP.md). Тут — технічний стек і архітектура.

## 1. Стек

| Шар | Вибір |
|---|---|
| Мова | **TypeScript** скрізь |
| Десктоп-оболонка | **Electron** (збірка через **electron-vite**) |
| UI | **React + Vite** |
| Полотно графа | **React Flow** (`@xyflow/react`) |
| Авторозкладка | **elkjs** |
| Стан і undo/redo | Власні **команди** + **Immer** (патчі); у вікні **Zustand** |
| Схеми та валідація | **Zod** |
| MCP | **`@modelcontextprotocol/sdk`**, транспорт Streamable HTTP на `127.0.0.1` |
| Стилі та компоненти | **Tailwind CSS + shadcn/ui** |
| Гарячі клавіші | **tinykeys** або `react-hotkeys-hook` |
| Тести | **Vitest** (логіка), **Playwright** (e2e для Electron) |
| Пакування | **electron-builder** (Windows / macOS / Linux) |
| Монорепо | **pnpm workspaces** |

## 2. Обґрунтування ключових рішень

### 2.1 Electron, а не Tauri
- MCP-сервер має жити в одній пам'яті з моделлю проєкту, щоб було одне джерело правди. Головний процес Electron працює на Node, тому офіційний TS MCP SDK запускається прямо в ньому.
- У Tauri бекенд на Rust. Довелося б або переписати доменну логіку й MCP на Rust, або тримати поруч окремий Node-процес і синхронізувати з ним стан. Обидва варіанти складніші.
- Розробник має вебовий досвід, тож увесь код лишається в TS/React.
- Мінус Electron — розмір збірки, приблизно 100+ МБ. Для інструмента розробника це прийнятно.

### 2.2 React Flow для полотна
- Панорама, зум, «вмістити в екран», мінікарта, виділення рамкою й перетягування зв'язків доступні з коробки.
- Вузли є React-компонентами з кількома точками підключення (handles). Тому блок вибору з окремим виходом на кожен варіант реалізується природно.
- Відкинуті альтернативи: JointJS (просунуті функції платні), Rete.js (складніший), власне полотно (надто дорого).

### 2.3 elkjs для авторозкладки
- Враховує порядок виходів (ports), тож стрілки від варіантів не перехрещуються.
- Підходить і для майбутнього показу повного графа зі сходженнями.
- Dagre простіша, але порядку виходів не розуміє.

### 2.4 Команди + Immer замість CRDT
- Будь-яка зміна є **командою**, яка виконується в головному процесі.
- `produceWithPatches` з Immer дає для кожної команди прямі та зворотні патчі.
- Спільна історія **undo/redo** для дій людини й агента.
- Синхронізація з вікном у **реальному часі** відбувається розсиланням патчів через IPC.
- Yjs/Automerge (CRDT) розраховані на кількох людей на різних машинах. Нам вони не потрібні й додали б складності.

### 2.5 Zod як спільна схема
Одна схема служить для трьох речей:
- валідація файлу проєкту при відкритті та імпорті;
- вхідні схеми MCP-інструментів (SDK приймає Zod напряму);
- TypeScript-типи через `z.infer`.

### 2.6 MCP через Streamable HTTP на localhost
- MCP-сервер має бути всередині вже запущеного застосунку. Тому stdio (де клієнт сам запускає процес сервера) не підходить. Натомість використовуємо HTTP на `127.0.0.1:<порт>`.
- Сервер слухає лише loopback-адресу, а доступ закритий токеном.
- Клієнти (Claude Code, Cursor тощо) підключаються за URL.
- Для клієнтів, які вміють лише stdio, у майбутньому можна додати маленький скрипт-міст. У MVP його немає.
- MCP доступний лише поки застосунок запущений і в ньому відкритий проєкт.
- **Підтвердження видалень:** команда агента, що видаляє контент, не виконується одразу. `ProjectStore` створює запит на підтвердження й надсилає його у вікно через IPC. Виклик MCP-інструмента чекає на відповідь людини або на таймаут. Деталі в [MCP.md](MCP.md), розділ 5.9.

### 2.7 Що свідомо не використовуємо
- **Tauri** — причина в розділі 2.1.
- **Redux** — Zustand + Immer простіші для цього обсягу.
- **БД (SQLite тощо)** — проєкт зберігається в одному JSON-файлі.
- **i18n-бібліотеку** — інтерфейс лише український. Рядки тримаємо в одному модулі, щоб потім легко додати інші мови.

## 3. Структура репозиторію

```
packages/
  core/                 чистий TS, без Electron і React
    schema/             Zod-схеми сховища: Project, Scene, Character, Block, Choice
      migrations/       міграції файлу проєкту між версіями
    export/             формат експорту: Zod-схеми, toExport(), fromExport(), міграції версій експорту
    commands/           команди зміни моделі (addBlock, link, deleteCharacter, ...)
    history/            undo/redo на основі Immer-патчів
    issues/             пошук проблем (осиротілі блоки, виходи без продовження, ...)
    queries/            пошук і фільтрація
apps/
  desktop/
    main/               Electron main process
      project-store/    поточний проєкт у пам'яті, виконання команд, історія
      persistence/      читання/запис файлу, автозбереження
      mcp/              MCP-сервер, інструменти як обгортки над командами core
      ipc/              міст main ↔ renderer
    preload/            безпечний API для renderer (contextBridge)
    renderer/           React UI
      canvas/           React Flow, кастомні вузли, розкладка через elkjs
      panels/           сцени, персонажі, проблеми, властивості блоку
      store/            Zustand-дзеркало стану
      hotkeys/
      strings/          українські рядки інтерфейсу
```

`core` — ядро системи. Його використовують і UI, і MCP, і він повністю покривається юніт-тестами.

## 4. Потік даних

```
 Людина (UI)                         AI-агент
     │                                   │
     │ IPC: command                      │ MCP tool call (HTTP, localhost)
     ▼                                   ▼
 ┌─────────────────── Electron main ───────────────────┐
 │  ProjectStore                                        │
 │   ├─ виконує команду (core/commands) через Immer     │
 │   ├─ записує патчі в History (undo/redo)             │
 │   ├─ перераховує проблеми (core/issues)              │
 │   └─ планує автозбереження у файл                    │
 └──────────────────────────────────────────────────────┘
     │ IPC: patches                       │ результат інструмента
     ▼                                    ▼
 Renderer (Zustand застосовує патчі)    Агент
```

- **Джерело правди** — `ProjectStore` у головному процесі.
- Renderer ніколи не змінює модель сам, а лише надсилає команди й отримує патчі.
- Undo/redo — це теж команди. Їх можна викликати з UI (Ctrl/Cmd+Z), а за потреби і з MCP.
- Позиції вузлів на полотні рахує розкладка (elkjs), у модель вони не потрапляють. Виняток — блоки, переставлені людиною вручну: їхня позиція зберігається в полі блоку `pos` (SCHEMA.md) і накладається поверх авторозкладки; службові вузли блоку (`(+)`, «Кінець», переходи) зсуваються разом із ним (`applyPinned` у `canvas/layout.ts`).

## 5. Зберігання

- **Сховище застосунку:** тека даних застосунку (`app.getPath("userData")`), наприклад на macOS `~/Library/Application Support/VNami/`:
  ```
  projects/
    prj_Zx7vB4nM2q.json        файл проєкту
    prj_Zx7vB4nM2q.v1.bak.json резервна копія перед міграцією (за потреби)
  settings.json                останній відкритий проєкт, порт і токен MCP, налаштування
  ui-state/
    prj_Zx7vB4nM2q.json        стан редактора: згорнуті гілки, зум, поточна сцена
  ```
- **Список проєктів** будується скануванням `projects/`: з кожного файлу читаються `id`, `name`, `description`, кількість сцен і дата зміни файлу. Окремого індексу немає, тож він не може розсинхронізуватися.
- **Перемикання проєкту:** поточний проєкт дозберігається, історія undo очищується, і завантажується інший. MCP одразу працює з новим активним проєктом.
- JSON форматується з відступами, а ключі йдуть у стабільному порядку.
- Кожна сутність має стабільний ID.
- **Версіонування:** файл проєкту має `version` формату сховища, а файл експорту — власну незалежну `version`. Міграції, резервні копії та поведінка з новішими файлами описані в [SCHEMA.md](SCHEMA.md), розділи 7–8.
- **Атомарний запис:** спершу у тимчасовий файл, потім перейменування.
- **Автозбереження:** таймер раз на секунду перевіряє прапорець «є незбережені зміни» і, якщо він стоїть, записує файл. Збереження не залежить від наявності проблем у проєкті.
- **Експорт** будує окремий файл через `toExport()` і дозволений лише тоді, коли `core/issues` не знаходить жодної проблеми з `severity: "error"`. Файл користувач зберігає куди завгодно через системний діалог.
- **Імпорт** приймає файл експорту будь-якої підтримуваної версії, мігрує його, перевіряє Zod-схемою й створює з нього новий проєкт.

### Збірка для Windows

```bash
pnpm dist:win
```

- Результат у `apps/desktop/release/`: інсталятор `VNami-Setup-<версія>.exe` (x64). Переносної версії немає: оновлюватися вміє лише інсталятор.
- Усі залежності вбудовані в зібрані файли (`out/`), тож у пакет потрапляють лише вони.
- Збирати можна й на macOS. Без Wine іконка та метадані `.exe` не змінюються (`signAndEditExecutable: false`), а підпису коду поки немає, тож Windows SmartScreen попереджатиме при першому запуску.
- Для збірки `pnpm` має бути в PATH (`corepack enable`).
- Це локальна збірка для перевірки. Справжні релізи збирає GitHub Actions (нижче).

### Оновлення

- **Звідки:** GitHub Releases публічного репозиторію `ValdekBro/vn-dialogs-builder` (`publish` в `electron-builder.yml`). У релізі — `VNami-Setup-X.Y.Z.exe`, `.blockmap` і `latest.yml` з номером версії. Безкоштовно.
- **У застосунку:** `src/main/updater.ts` на `electron-updater`. Перевірка через 5 с після запуску й кожні 4 год; `autoDownload` вимкнено. Стан (`UpdateState` у `shared/api.ts`) приходить у вікно подією `update`; вікно показує плашку (`UpdateBanner`) і кнопку «Перевірити оновлення» на екрані «Проєкти». «Оновити» → завантаження → `store.dispose()` (дозбереження) → `quitAndInstall` (тихе встановлення й перезапуск). Фонова перевірка без інтернету нічого не показує.
- Працює лише у встановленій Windows-збірці. У `dev` і на інших платформах стан `unsupported`.
- **Випуск версії:**
  1. Закомітити зміни.
  2. `pnpm release 0.2.0` — піднімає версію в `package.json` (корінь і `apps/desktop`), комітить, ставить тег `v0.2.0` і пушить.
  3. GitHub Actions (`.github/workflows/release.yml`, `windows-latest`): перевіряє, що тег збігається з версією, проганяє typecheck і тести, збирає інсталятор (з іконкою й метаданими `.exe` — на Windows є rcedit) і публікує реліз: спершу створює чернетку (`gh release create --draft`), electron-builder завантажує в неї файли (`--publish always`, `GITHUB_TOKEN`), далі чернетка публікується. Так паралельні завантаження не створюють двох релізів з одним тегом.
  4. Опис змін («Що нового») — дописати в реліз на GitHub. Плашка веде на сторінку релізу.
- Для публічного репозиторію хвилини GitHub Actions безкоштовні.
- Підпису коду немає: SmartScreen попереджає при першому встановленні, на оновлення це не впливає.

## 6. Безпека

- MCP слухає тільки `127.0.0.1`.
- Доступ до MCP закритий токеном, який застосунок генерує й показує в налаштуваннях разом із готовою командою підключення.
- В Electron: `contextIsolation: true`, `nodeIntegration: false`. Renderer спілкується з main лише через вузький API у preload.

## 7. Тестування

Повна стратегія і список сценаріїв — у [TESTING.md](TESTING.md). Коротко:
- **Vitest** для `core`: команди, undo/redo, пошук проблем, схеми. Це основне покриття.
- **Vitest** + справжній MCP-клієнт для MCP-інструментів над `ProjectStore`.
- **Playwright E2E** (лише на запит, для регресійної перевірки) запускає справжній Electron-застосунок з окремою текою даних і проходить сценарії з FLOWS.md кліками й введенням тексту: від створення блоків до роботи разом з агентом через MCP.
- Для тестованості застосунок має тестовий режим (`VN_E2E=1`), теку даних з env (`VN_USER_DATA_DIR`) і стабільні селектори (`data-testid` з ID сутностей).
